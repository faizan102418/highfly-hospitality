# Render staging provisioning and verification runbook

**Purpose:** provision and verify an isolated cloud staging environment for the La Serene HMS front-desk release candidate.  
**Safety boundary:** this runbook does not authorize production access, deployment, migrations, credential rotation, or restore. Production must remain untouched.

## Current repository contract

The primary Render Blueprint, `render.yaml`, now declares both existing development resources and these additional staging resources:

- Web service: `highfly-hospitality-staging`
- PostgreSQL resource: `highfly-hospitality-staging-db`
- Database name/user: `highfly_hospitality_staging` / `highfly_hospitality_staging`
- Region: Singapore
- Commit-triggered auto-deploy: disabled for staging
- Staging build command: does not run Alembic migrations
- Staging `HMS_DATABASE_URL`: references only `highfly-hospitality-staging-db`
- Staging `HMS_SECRET_KEY`: independently generated by Render

The standalone `render.staging.yaml` remains available for a separate staging-only Blueprint if desired. Do not sync both configurations in a way that attempts to create duplicate resources. The Blueprint is desired configuration, not proof the resources exist.

The staging service's startup migration guard expects the database schema to be at the application head; a newly created empty database will not pass readiness until an authorized operator has reviewed and performed the controlled migration. Do not add migrations back to the staging build command to bypass this gate.

## Provisioning and isolation checklist

Complete these steps in the Render dashboard as an authorized operator:

1. Open the existing `highfly-hms` Blueprint and inspect the proposed changes before syncing. The only intended resource additions are `highfly-hospitality-staging` and `highfly-hospitality-staging-db`; the existing development service/database definitions must remain unchanged.
2. If Render proposes replacing, deleting, renaming, or repointing development resources, cancel the sync and investigate.
3. Review the service/database names, database name, region, staging auto-deploy setting, and migration-free staging build command shown above. Provision/sync the Blueprint only after reviewing the full plan.
4. Record the staging web service ID, staging database ID, region, and generated staging HTTPS hostname in the private release evidence record. Do not record connection strings, usernames/passwords, tokens, or environment-variable values.
5. In the staging web service's Environment settings, verify `HMS_DATABASE_URL` is sourced from `highfly-hospitality-staging-db` via the Blueprint database connection-string reference. Verify `HMS_SECRET_KEY` is independently generated for staging. Do not copy DEV or production secrets into staging.
6. In the staging database's Info/Networking view, verify the database name/resource identity. Review inbound networking; prefer private service-to-database connectivity and remove broad public inbound rules when supported and after connectivity is confirmed.
7. Confirm the DEV service still points only to `highfly-hospitality-dev-db`. Do not change its environment or database while provisioning staging.
8. Before deploying an application candidate or migrating staging, record the exact commit SHA, database target, current schema revision if available, migration plan, rollback owner, and last known-good revision. Obtain explicit operator approval for deployment and migration. No production target is allowed.
9. Use only synthetic guests, synthetic identifiers, test-only accounts, and synthetic financial amounts.

## Readiness smoke workflow

After an authorized operator has completed deployment and the staging schema is at the expected revision, run **Actions → Staging readiness smoke check → Run workflow** and enter the staging HTTPS base URL, for example the URL assigned to `highfly-hospitality-staging`.

The workflow:

- requires HTTPS and a hostname containing `staging`;
- refuses the known development hostname;
- calls only `/api/ready`;
- requires HTTP 200, `status=ready`, and `mode=postgresql`.

A green workflow proves only that the entered staging hostname responded and its readiness endpoint could query PostgreSQL. **It does not prove database identity or tenant isolation.** The operator must independently verify the Render service-to-database attachment and resource IDs in the provider control plane and record that evidence.

## Release gates after readiness

- [ ] Service and database are distinct staging resources, and attachment is verified in Render.
- [ ] Staging uses independently generated secrets and no DEV/production database or secrets.
- [ ] Readiness smoke workflow passes against the staging hostname.
- [ ] Candidate SHA and deployed Alembic revision are recorded.
- [ ] Tenant-negative and manual front-desk acceptance tests pass with synthetic data.
- [ ] Folio, payments, ledger, room state, and housekeeping reconciliation is exact.
- [ ] Isolated recovery drill is approved by an authorized operator and completed using synthetic staging data only.
- [ ] Release owner records GO/NO-GO and rollback details.

Until every required gate has evidence, release status remains **NO-GO**. This PR changes repository configuration and documentation only; it does not provision Render resources, deploy application code, run migrations, or perform a restore.
